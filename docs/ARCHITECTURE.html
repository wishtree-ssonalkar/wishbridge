The big picture

WishBridge builds on the Databricks Labs migration toolkit (LakeBridge): the toolkit analyzes and converts the code; WishBridge adds the fit check, fix rules, Claude, deployment, data copy, comparison, reports and the screens. It has three layers:

Entry points start the same app; the shell opens a project and hands it to the warehouse package named in its project.yml.

1 · Shared shell - src/wishbridge/

2 · Warehouse packages - src/wishbridge/warehouses/<warehouse>/

Each warehouse - bigquery, datastage, informatica, netezza, oracle, redshift, snowflake, sqlserver, ssis, synapse, teradata - is a complete, independent copy, so it can analyze, convert and copy data its own way and a change for one warehouse cannot break another. ssis/ is the reference copy for fixes that apply to all (see Changing WishBridge).

Servicesdbx.py SQL warehouse · lakebridge.py toolkit · ai.py Claude · inventory.py client database (read-only) · state.py results · config.py settings
Background runsrunner.py starts python -m wishbridge pipeline …, writes run_status.json (the page shows progress from it) and pipeline.log
Screensui/main.py step bar · ui/steps/<tab>.py one tab each (settings, code, run, fix, data, report, share) · ui/claude_panel.py

The pipeline

Each step is one module with one main function; its result is saved in output/state.json, which the screens read. Steps run in the background, one after another.

Blue: assessment (no Databricks needed) · green: code migration · amber: data migration · red: reports and zips.

3 · The project folder - the data

<project>/
  project.yml            all settings (no passwords - ever)
  input/                 the client's code as received
  database_code/         tables and procedures read from the database
  overrides/             hand fixes (Fix code) - used on every later run, never overwritten
  output/state.json      every step's result (the screens read this)
  output/final/          converted code
  output/logs/           pipeline.log, run_status.json, toolkit_<step>.log
  output/review_package/ the zips

On the laptop it is a folder. In the Databricks App the whole folder is kept as one zip on the projects volume and unpacked into the app's working folder when opened (hosting.push / hosting.pull).

Laptop and Databricks App

The same code and screens. hosting.is_app() is true inside Databricks Apps (DATABRICKS_APP_NAME). A choice that cannot work where you are shows "On the laptop only" and what to use instead (hosting.LAPTOP_ONLY) - it is never hidden. Differences live in hosting.py and in a few clearly marked if hosting.is_app(): branches in the screens. The app runs Python 3.11 (no 3.12-only syntax - tests/test_python311.py).

Changing WishBridge

A fix for every warehouse (most fixes) 1. Change the file in ssis/.
2. python tools/sync_warehouses.py <file>
3. Run the tests.
A change for one warehouse only 1. Change the file in that warehouse's folder.
2. Add it to that folder's CUSTOMIZED.txt with why, e.g. analysis.py - Teradata BTEQ scripts are analyzed per statement.
The safety net tests/test_warehouse_drift.py fails when a shared file differs from ssis/ - a fix forgotten in some warehouses - and says how to fix it. --check shows the same.

Install, deploy and use

WishBridge runs on a laptop (desktop) and as a Databricks App. Same code, same screens; pick per client and per phase. Full step-by-step guides: docs/USER_GUIDE.md (laptop) and docs/DATABRICKS_APP.md (app).

Laptop (desktop)

1 · Install once (about 20 minutes) Get the folder: git clone https://github.com/wishtree-ssonalkar/wishbridge.git C:\wishbridge (or the ZIP from GitHub). Double-click Install WishBridge.cmd. It installs what is missing (Python, Java, Databricks CLI), opens a browser to sign in to Databricks, installs the migration toolkit and its converters, installs WishBridge and adds a desktop icon. Safe to run again; -DryRun shows what it would do. macOS / Linux: ./install.sh.
2 · Start The Wishtree WishBridge desktop icon (or Start WishBridge.cmd). The app opens in the browser at http://localhost:8501 and only listens on this computer. Close the window to stop it.
3 · Use Sidebar: Check this computer (installs anything missing) → choose Assessment, Code migration or Data migration → open a folder, upload the code (zip), open the assessment zip or a project → work through the tabs. Projects live in C:\WishBridge\Assessments and C:\WishBridge\Migrations.
4 · Update cd C:\wishbridge → git pull → restart WishBridge. (WishBridge is installed from this folder, so a pull is the update; if it adds packages, run Install WishBridge.cmd again.) A sign-in that expired: databricks auth login --profile DEFAULT.

Databricks App (deployed on Databricks)

1 · Before you deploy On a laptop with WishBridge's folder and the Databricks CLI: a login to the workspace (databricks auth login --profile CLIENT), the right to create apps, a SQL warehouse ID (SQL › SQL Warehouses), a catalog for the projects volume and the catalog(s) for the test schemas.
2 · Deploy (one command, about 5 minutes) .\deploy-databricks-app.ps1 -Profile CLIENT -WarehouseId <id> -ProjectsVolume /Volumes/<catalog>/wishbridge/projects -TargetCatalogs <catalog> -ShareWith <team-group> - creates the volume, the app (with the SQL warehouse), the permissions, checks the code compiles, uploads and starts it, prints the link.
2b · Or deploy from Git Databricks › Compute › Apps › wishbridge › Deploy › from Git, repository wishtree-ssonalkar/wishbridge, the branch with the app (Shubham/WishbridgePhase1, or main after the merge). app.yaml and requirements.txt at the repository root are what Databricks reads. In a new workspace run the script once for the permissions and the sql-warehouse resource.
3 · Give access Databricks › Compute › Apps › wishbridge › Permissions → CAN USE for the people or group. They open the link and sign in with their usual Databricks account (single sign-on).
4 · Use The same screens. The sidebar's App check shows the workspace, warehouse, project storage and the migration toolkit (installed by itself about a minute after the app starts). Projects are saved in the workspace after every change - Open a project lists them.
5 · Update Run the same deploy command again: only changed files are uploaded, the projects stay. Run the tests first (pytest).
6 · Run it day to day Logs: databricks apps logs wishbridge --profile CLIENT. A running app costs compute: stop it when not needed - databricks apps stop wishbridge / start wishbridge. Remove it: databricks apps delete wishbridge (the projects stay on the volume).

Tests and deployment

  • pytest - 328 tests that run without Databricks, the toolkit or a database (stand-ins replace them); UI tests use Streamlit's AppTest.
  • Run the tests before every deployment; deploy-databricks-app.ps1 also refuses code that does not compile.
  • Commit to Shubham/WishbridgePhase1; merge to main with a pull request.
